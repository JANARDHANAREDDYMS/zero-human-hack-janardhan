Cross-cutting controls and later boundaries

Harness-owned state

RunState records stage, status, timestamps, calls, tokens, cost, corrections, event history, artifact pointers, and structured error. Each external stage receives a copy of relevant state rather than an unbounded chat.

Usage and time limits

Before each stage: check elapsed time, call count, and remaining tokens/cost. Pass allowances into the backend. Record reported usage before checking overruns.

The future transport must enforce its own request timeout and generation cap. A synchronous in-flight call cannot be canceled by this harness, and provider charges cannot be reversed.

Explicit terminal outcomes

completed: accepted population published.
incomplete: invalid input/specification or rejected review.
limit_exceeded: call/token/cost/time boundary reached.
failed: backend/infrastructure error.

Consumers must check state.json, not infer success from a file's existence. Interrupted processes may leave running state and partial artifacts; resume is not implemented.

Atomic per-file storage

Write to a temporary file and atomically replace it. Preserve every revision and call snapshot in an isolated run directory. This is per-file atomicity, not a transaction across the entire run.

Model-function client · built and intake verified

Python → configured HTTPS project function, authenticated by a dedicated bearer token. Stage, model, usage, instruction version/hash, and output envelope are checked. No automatic switch to another provider or fixtures.

The deployed Lovable server route completed one authenticated intake call. Larger schemas, full generation quality and sponsor-credit billing remain unverified.

Exa adapter · built

POST /search with page text, at most two queries and three results per query by default. Deduplicate URLs, preserve source IDs and bounded text, record provider cost estimates, and reject extraction that changes the retrieved catalog.

Verified with mocked transport only. Actual credentials, credits, and search quality have not been tested.

Seven required qualitative checks
  1. Coverage: important needs, alternatives, existing solutions, and omitted situations.
  2. Segment distinctness: meaningful purchasing contexts rather than redundant labels.
  3. Within-segment variation: diverse but compatible goals, budgets, deadlines, requirements, and decision behavior.
  4. Evidence support: source-qualified claims and legitimate references.
  5. Assumption transparency: invented ranges/counts stay explicit assumptions.
  6. Product independence: no customer engineered to choose the client or reject its weaknesses.
  7. Simulation fit: usable attribute names, units, operators, purchasing scope, and unknown handling.

Every check requires pass/warning/fail, a rationale, and relevant IDs. IDs must exist in the evidence/specification/pilot. Every failed check needs a blocking finding with a matching category code. Acceptance with failures or blockers is rejected in code. A fixable revision uses the existing one-correction allowance and then re-runs validation and review.
